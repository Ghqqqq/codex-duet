# Native dispatch fallback

Native `Agent(subagent_type: "codex:codex-native", …)` dispatch is the default from the first assignment. Load this skill only for the triggers in its description. Browser work and Computer Use run natively; they do not by themselves require fallback.

## Bash dispatch

Use background `duet task` only when the native agent returns `native_adapter_unavailable` or `native_capacity`, a per-call option is rejected by the `DUET:` line (`--run`, `--approve-browser-origin`, `--approve-computer-app`, `--lease-sec`, `--question-timeout-sec`), or following up a worker launched through Bash. For that fallback, use one Bash call per job with `run_in_background: true` and `description: "Codex: <label>"`. When Claude's Bash sandbox is on, set `dangerouslyDisableSandbox: true` on the tool call: the runtime needs network and local sockets. Use the installed `duet` launcher; if PATH is stale, reload/start a new session or use the absolute `bin/duet` path two directories above this skill's base directory.

```bash
duet task --model gpt-6.1-sol --effort xhigh --normal <<'DUET_TASK'
<brief>
DUET_TASK
```

- Pass the brief on stdin, never on the command line. Use a single-quoted `DUET_TASK` heredoc (`DUET_ANSWER` for answers), with its delimiter absent as a complete line from the text; single-quote dynamic runtime arguments separately. Simple `duet` commands can be auto-approved; double quotes, pipes, compound shell commands and flags outside the permission hook's allowlist use normal permissions. Respect the user's model, effort and speed choices.
- Investigators and reviewers add `--sandbox read-only`. Another checkout requires `--cwd '<dir>'`. Parallel implementers share the checkout only with non-overlapping OWNED PATHS. Otherwise serialise them, or create separate worktrees with `git worktree add`, pass each as `--cwd`, and merge the branches yourself.
- `duet task` implies `--direct`: a detached job with this process attached as its sole owner wait. Progress appears in `/tasks`; the report arrives with the background-task completion notification. Only if it is missing, run `duet result <worker>`. Never parse an output file, poll, sleep or use `tail -f`; never re-spawn a worker that is still running or run two waits for one job. Retain `worker` and `jobId`; use the job ID to select an older turn.
- Report v2 starts with `status`, `worker`, `jobId`, `summary` (up to 8000 characters, with `summaryTruncated` when cut). Nonempty evidence follows: `blockers`, `question`, `changedFiles`, `checks.ran`/`checks.claimed`, `assumptions`, `keyFindings`, and `usage` (optional integer `inputTokens`, `cachedInputTokens`, `outputTokens`, `reasoningOutputTokens`, `totalTokens` for that turn only; omitted when unknown). Lists and text may be shortened to fit the 2000-byte envelope excluding summary; `question.optionsOmitted` and `blockers[].question.optionsOmitted` count omitted choices. Compact blockers retain bounded app/tab/session and safe approval identifiers, and cleanup status when known. `next` is the suggested action or null; `details` is `duet result '<jobId>' --details`, always targeting that exact job for full evidence, handles, settings and artifact paths. Use details for acceptance when the compact report omits evidence; never read `rawOutputFile` unless a report field is insufficient.
- A `thread_busy` refusal points `next` to the owning job's pinned answer when it has a question, otherwise recovery/status, or null. Its blocker contains the owner question/cancel action when available; `details` still targets the refused job. Do not submit another task on the busy thread. Denied/unsupported server requests force `blocked` even if Codex claims completion; retain `approval_denied`/`approval_unsupported` and their safe method/kind/server/origin identifiers.
- Terminal status: run the applicable acceptance protocol, even if Bash exited nonzero. Exit codes are 0 for `completed`, 2 for `blocked`/`needs_input`, and 1 for other terminal states; non-terminal returns exit 0 for `running`/`needs_answer`, 2 for `ownership_moved`, or 130 for a stopped owner wait.
- `running`: run `duet wait <worker>` in background Bash and wait for its notification. An expired unanswered slot does not make the wait return early; it keeps waiting under its normal rules. `--quiet` suppresses progress; the direct wait budget defaults to 3600 s (maximum 3600), and the lease to 1800 s. Do not combine direct mode with `--follow`, `--detached`, `--background`, `--json`, `--feed-limit` or `--min-interval-sec`.
- `needs_answer`: Use the report's `next` command verbatim, or run `duet answer <worker> --question '<questionId>'` with the displayed `question.id` in ONE background Bash call (`run_in_background: true`, `timeout: 600000`), with stdin via `<<'DUET_ANSWER'`, the answer, then `DUET_ANSWER` alone. It resolves the owner, refuses a stale/expired question, explicit owner mismatch, expired lease or stopping job, submits once and keeps the sole wait attached. A bare `duet answer <worker>` answers whatever question is pending now, which may be newer than the one you saw. Never pass the answer on the command line or start a second wait. Answer from your context when the brief should have covered it (and note the brief defect), otherwise collect it for the user. A `question.kind` of `approval` is a Computer Use app request with four fixed options; forward it with `AskUserQuestion` unless the user pre-authorised the app. Submit only an exact displayed label (`Allow this call`, `Allow for this task`, `Allow always (isolated Codex home)`, `Deny`), its number `1`–`4`, or a single keyword `call`/`once`/`task`/`always`/`deny`/`no`. Answers are trimmed and case-insensitive; exact labels allow a trailing period. Anything else, including `yes`, negations, qualifications and mixed text, denies the request. Do not append an explanation or infer permission from ambiguous text. Use `--details` if question text/options were shortened. The answer continues the same turn.
- `ownership_moved`: report it; never reuse the retired owner, re-adopt or submit a replacement task. `error`: validation errors occur before dispatch; runtime or wait errors can occur after launch, so check `duet status` before resubmitting. `owner_stopped`: the wait was stopped and the job is interrupted; inspect `duet result <worker> --details` for recovery handles.
- Stop the background task in Claude Code (interrupts the turn as `owner_stopped`), or run `duet cancel <worker>`. The thread and edits persist. Continue a user-stopped job only with the user's consent, using `duet task --to <worker>` with a new brief or `duet task --continue <jobId> --cwd '<cwd>'`. Never continue it automatically just because `next` suggests a follow-up. With consent, an unfinished adoptable job needs `duet adopt <jobId> --json` first, followed by one `duet wait <jobId> --owner '<newOwnerId>'`, not a new task.

`--to`, `--thread` and `--resume`/`--resume-last` inherit recorded model, effort, sandbox and speed from a started attempt; explicit flags override them. An explicit `--thread` can inherit these settings across sessions. Request grants are inherited only from the original dispatch in the same Claude session, excluding runtime-only approvals and foreign dispatches after adoption. `--continue` inherits the selected job's settings and eligible request grants; when its sandbox is missing, pass `--sandbox` explicitly to resolve `thread_settings_unknown` (a recorded sandbox cannot be overridden with `--continue`). State `--sandbox read-only` again for a read-only follow-up and `--normal` when resetting fast mode. `--fork` imports the current Claude transcript into a new Codex thread for a fresh assignment, then runs the stdin brief; use it under the protocol's **Forking context** rules. It is labelled “imported Claude conversation (fidelity not verified)”; do not assume lossless context. It cannot combine with `--to`, `--thread`, `--continue` or resume flags; follow up afterwards with `--to`.


Run `duet task --help` for flags. Choose model and effort for the assignment and selected mode; the displayed `gpt-6.1-sol` example is ultra's built-in routine model. Use the effective models named by the mode reminder or status (saved with `duet setup --default-model`); explicit user settings take precedence.

Task text belongs in briefs, never control-CLI arguments or a generated shell command. For a permitted Bash fallback, send the brief on stdin through a single-quoted `DUET_TASK` heredoc; never interpolate raw slash arguments into executable shell source.

## Follow-ups and recovery

- Follow-ups and rework use SendMessage to the named native agent, or `duet task --to <worker>` with a new brief on stdin. They start a new job on the same thread in the original cwd; restate the relevant criteria. Codex does not remember your acceptance notes.

Check `duet status` before retrying an unavailable native adapter: dispatch is unconfirmed. Run `/reload-plugins` to restore the hooks. When native adapter capacity is full, wait for active workers to finish or stop them before starting a new native agent; the Bash fallback above remains available.

## Forwarding-agent fallback

Fallback only: use `Agent(subagent_type: "codex:codex-worker")` when neither native dispatch nor background Bash is available, or the user asks for a forwarding-agent transcript. Never pass `model` or `effort` to that Haiku forwarder; put Codex's choices in the assignment text. Follow-ups use a NEW fallback agent with `duet task --to <worker>`; SendMessage to an existing fallback agent is only for its pending question.
